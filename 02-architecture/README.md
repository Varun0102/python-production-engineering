# Architecture

See page 10 of 03-diagrams/python-production-engineering.drawio.

## Components

| Component | Where it runs | Job |
|---|---|---|
| EC2 workstation | AWS, your own instance | Where you write code, build images and run kubectl |
| GitHub repository | GitHub | Source code and pull requests |
| Amazon ECR | AWS | Stores the Docker image |
| Amazon EKS cluster | AWS | Runs the service |
| Kubernetes Service (LoadBalancer) | EKS | Public entry point for requests |
| Deployment, 2 pods | EKS | The Complaint Triage Service: Uvicorn, FastAPI, Pydantic, async httpx, JSON logs |
| ConfigMap | EKS | ENVIRONMENT, LOG_LEVEL, AI_API_URL |
| Secret | EKS | AI_API_KEY |
| Liveness and readiness probes | EKS | Call GET /healthz |
| AI model stub | EKS | A fake AI service. No real key, no cost. Can be slow or wrong on purpose |

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | /triage | Send a complaint, get category, priority and team |
| GET | /healthz | Is the service healthy? |
| GET | /docs | Interactive API documentation generated by FastAPI |

## Deployment flow

    Code on EC2 --> git push / PR --> docker build --> push to ECR --> kubectl apply --> Running on EKS

## Concept: why the nodes are in public subnets

To keep the lab simple, the EKS nodes run in public subnets. In a real company they run in private subnets, and only the load balancer is public.
